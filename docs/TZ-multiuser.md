# Техническое задание: профили пользователей Git Support

## 1. Цель и границы

Добавить учебный многопользовательский режим поверх действующего Git Support. У каждого профиля свои настройки, чаты и расходы RouterAI. База знаний, поисковый индекс и эталоны RAG общие. Исходная точка — актуальная `main` с проверенным публичным HTTP доступом. После отдельного указания начать реализацию в новой ветке от `main`.

Вход только по никнейму, без пароля, электронной почты, привязки к устройству. У профиля `admin` есть право менять общие настройки. Любой, кто знает ник, может войти в этот профиль, увидеть его чаты и вызвать RouterAI за его счёт. В частности, вход по известному нику `admin` также позволяет менять общие настройки. Такой вход пригоден для учебного сценария и не является защитой профиля от человека, знающего ник. Публикацию и обновление VPS согласовать отдельно. Текущий публичный HTTP не защищает трафик при передаче ключа.

## 2. Вход, выход и интерфейс

1. При открытии сайта без сессии показать страницу входа с полем «Никнейм» и кнопкой «Войти». Первое использование ника создаёт профиль, повторное открывает тот же профиль. После успешного входа открыть существующий интерфейс с четырьмя вкладками: «Чат», «База знаний», «Тесты RAG», «Настройки». Порядок и оформление вкладок сохранить.
2. Предлагаемое правило идентичности ника: убрать пробелы по краям, привести Unicode к NFC, для сравнения использовать `casefold`, сохранить исходное отображаемое написание. Разрешить от 1 до 32 букв, цифр, дефисов и подчёркиваний. Проверить уникальность нормализованного ника ограничением в БД. Одновременные входы по одному новому нику создают один профиль. `Admin` и `admin` открывают один профиль.
3. При входе сервер выдаёт сессию с непрозрачным случайным идентификатором в `HttpOnly` cookie. Хранить на сервере связь идентификатора с пользователем и сроком действия. При выходе отозвать текущую сессию и очистить cookie. Показать текущий ник и кнопку «Выйти» в существующей шапке. Обновление страницы сохраняет активную сессию. Выход очищает личные данные из состояния фронтенда, чтобы следующему профилю не показать предыдущие чаты и настройки.
4. Все `/api/*` требуют действующей сессии, за исключением входа и запроса статуса сессии, если он предусмотрен интерфейсом. Для API без сессии вернуть `401`. Страницу входа, её ресурсы и `/health` сохранить доступными до входа. Существующие проверки Host и Origin сохранить. Cookie должна работать в текущем учебном режиме HTTP и использовать `Secure` при работе через доверенный HTTPS.

## 3. Личные и общие данные

| Область | Требование |
| --- | --- |
| Ключ RouterAI | Личный. При первом входе отсутствует. Показывать только статус «ключ сохранён». |
| Системный промпт | Личный. Новый профиль получает базовый промпт приложения. |
| Пороги поиска | Личные значения Vector и BM25 и два переключателя применения. Инициализировать действующими значениями по умолчанию. |
| Беседы | Личные список, история, сообщения, резюме и снимки источников в ответах. |
| Вызовы RouterAI | Личные журнал, фактические расходы и диагностика. |
| RouterAI и API Base URL | Общие параметры подключения. `admin` выбирает API Base URL RouterAI, остальные профили видят его в режиме просмотра. |
| Embeddings и токенизатор | Общая модель `baai/bge-m3` и согласованный токенизатор для поиска и индексации. Модель фиксирована для всех профилей, включая `admin`, на этом этапе. |
| Подготовка документов | Общий обработчик. По умолчанию локальный. `admin` выбирает из доступных обработчиков, остальные профили видят текущий выбор. |
| Модель генерации | Общая модель. `admin` выбирает модель генерации, начальное значение берётся из действующей установки. |
| База знаний и тесты RAG | Общие документы, подготовленные чанки, активный индекс и набор эталонов. Ответы на эталоны остаются в личном чате. |

Любой вошедший пользователь может просматривать, загружать, заменять и удалять общие документы, подготавливать чанки и запускать индексацию. Изменения общей базы видны всем. `admin` получает унаследованные личные данные и право менять общие настройки. Право проверяется на сервере по профилю текущей сессии. Попытка другого профиля изменить общие параметры через API возвращает `403`. Личные параметры редактируются только в своём профиле, включая `admin`.

Base URL выбирается из разрешённых HTTPS адресов RouterAI, заданных в конфигурации установки. Проверять адрес на сервере до сохранения и до отправки ключа. При перенаправлении на адрес вне списка отклонять запрос. Это защищает ключи пользователей от отправки на сторонний сервер через изменение общей настройки.

## 4. Ключи, платные операции и учёт расходов

1. Источник `user_id` для всех операций — серверная сессия. Запросы браузера не могут назначать владельца, передавать чужой `user_id` или выбирать идентификатор ключа. По идентификатору беседы проверять принадлежность текущему пользователю при чтении и записи. Для чужого идентификатора возвращать `404`, как для отсутствующей беседы. Списки, архив, резюме, диагностические события и итоги расходов всегда фильтровать на сервере.
2. Платные вызовы поиска, разбиения запроса, резюме, ответа, тестирования и индексации, а также обращения за стоимостью вызова используют ключ инициатора. Без ключа вернуть понятную ошибку до постановки платной операции в очередь и до обращения к провайдеру. Ключ `admin` и прежний общий ключ не используются как запасные.
3. При старте фоновой индексации зафиксировать пользователя и версию ключа. Передать контекст явно в задачу; задача не должна зависеть от последующего выхода, входа другого пользователя или смены ключа. В пределах одной операции использовать один снимок действующего ключа, в том числе для повторов и уточнения стоимости. При смене ключа следующие операции используют новую версию. Исходный секрет допускается держать в памяти задачи, без записи в очередь, данные индекса и логи.
4. Для каждого фактического вызова фиксировать `user_id`, непрозрачный идентификатор версии ключа, идентификатор вызова или группы, тип операции, модель, статус, время и фактическую стоимость. Неизвестную стоимость учитывать отдельно. Смена ключа не переносит и не обнуляет историю. Итоги считать по пользователю, а при детализации — по версии ключа. Сохранять существующую точность начислений и округление интерфейса. Прежнее решение об отсутствии лимитов расходов сохраняется.
5. Хранить ключи в постоянном серверном хранилище секретов на базе существующего файла `.env` в `/app/data` для контейнера и локального `.env` для разработки. Идентификаторы профилей и версии хранить в SQLite. Синхронизировать обновление файла, чтобы параллельные сохранения не затирали чужие записи. Ключ не возвращать в API после сохранения, не писать в логи и сообщения ошибок, не передавать в URL и не включать в образ, Git или тесты. При чтении настройки или диагностической записи убедиться, что сырой ключ и заголовок `Authorization` не попадают в ответ.

## 5. Общий индекс и параллельные операции

Сохранить действующие SQLite, Qdrant Local, чанкинг, BM25, RRF и правила переключения поколений. Все пользователи ищут по одному активному индексу в одной модели embeddings, но применяют свои пороги. При индексации оставить существующее ограничение конфликтующих изменений и не переключать активное поколение до успешного завершения. Ошибка операции не должна подменить предыдущий рабочий индекс. После успешной индексации в профиле A результат должен находиться из профиля B без новой индексации со стороны B. Общий индикатор прогресса показывает состояние операции без ключа и чужой финансовой детализации.

## 6. Миграция существующей установки

1. Использовать штатную миграцию Alembic после `0006_chat_conversations.py`. Добавить сущности пользователя и сессии, привязку личных настроек, бесед и событий к профилю. Сохранять существующие идентификаторы бесед, сообщений, документов и поколений индекса. Определение модели и запросы к данным оставить в слое доступа к БД.
2. Создать профиль `admin` при переходе со старой схемы до открытия входа. Назначить ему существующие чаты, архив переписки, личные настройки, события и расходы. Сохранить прежний ключ RouterAI за `admin` через серверный файл секретов. Исторические вызовы, для которых версия ключа неизвестна, отмечать как исторические с неизвестной версией. Общие настройки установки сохранить с актуальными значениями, совместимыми с существующим индексом.
3. Не копировать SQLite, Qdrant или документы для каждого пользователя. Сохранить общий корпус, чанки и текущий индекс. Новые профили создаются без ключа, расходов, событий и чатов. После перезапуска контейнера и повторного прогона переноса не должно быть повторного начисления, второго `admin`, сброса настроек или перезаписи нового ключа старым. Миграцию БД и перенос файла секретов сделать устойчивыми к прерыванию между шагами. Пока обязательный перенос не завершён, не открывать вход с неполными данными. Для чистой установки учитывать отсутствие старых данных и ключа.
4. Проверять перенос на копии БД и синтетическом `.env`, в отдельном каталоге Qdrant. Перед применением к рабочему серверу подготовить резервную копию `/app/data` и описать восстановление на случай ошибки.

## 7. Точки изменения

- `app.py` — страница входа, сессия и проверка пользователя для всех текущих групп API: настройки, документы, индекс, тестирование RouterAI, журнал и чат.
- `src/database.py`, `migrations/versions/`, `src/repository.py`, `src/chat_repository.py` — схема, перенос, выборки по владельцу, стоимость и архив.
- `src/service.py`, `src/embeddings.py`, `src/rag_answer.py`, `src/chat_context.py`, `src/rag_service.py`, `src/indexing.py` — передача профиля, снимка ключа и учёт всех вызовов. Проверить также непрямые вызовы поиска и получения стоимости, чтобы исключить обращение к глобальному ключу.
- `static/index.html` и существующие скрипты — вход, выход, отображение ника и личных настроек. Страницу тестов и меню сохранить. Обновить руководство для пользователя и инструкцию развёртывания с нюансами миграции.

## 8. Приёмка

1. Без сессии `/health` и вход доступны, личные и общие API закрыты. Первый вход `user1` создаёт чистый профиль. Выход и повторный вход возвращают сохранённые данные. Вход `user2` из того же браузера показывает его данные без остатков интерфейса `user1`.
2. `user1` и `user2` видят один набор тестов RAG, одни документы и один активный индекс. Изменение промпта, порогов и ключа `user1` не меняет настройки `user2`. Попытки читать или отправлять сообщения в чужую беседу по ID отклоняются. Оба профиля имеют все четыре вкладки и одинаковые права на общие документы. Изменения Base URL, модели генерации и обработчика из сессии `admin` видны всем. Запись этих настроек из обычного профиля через API возвращает `403`. Модель embeddings остаётся неизменной.
3. У `user1` и `user2` задать разные фиктивные ключи. Через подставной RouterAI проверить вызовы чата, тестовых кнопок, индексации, повторов и расчёта стоимости. Убедиться, что они идут с ключом инициатора, а журнал и итог соответствуют его профилю. Смена ключа между запуском и завершением индексации не меняет уже запущенную задачу. Профиль без ключа не вызывает RouterAI.
4. `user1` загружает и индексирует документ, `user2` находит его в общем индексе. Расход на индексацию видит только `user1`. Ошибка индексации оставляет прежнее активное поколение. Загруженный корпус и настройки переживают перезапуск.
5. На копии существующей установки проверить точность переноса в `admin`, повторный запуск миграции, отсутствие дублирования истории и недоступность данных `admin` из других профилей в рамках их сессий. Сам вход с ником `admin` открывает унаследованный профиль по правилам учебного режима.
6. Прогнать локальные тесты и регрессию Host/Origin, проверить `/health`, интерфейс, Linux/amd64 и `/app/data` в контейнере. Для автоматических тестов использовать фиктивные ключи и имитацию RouterAI. Отложенный старый тест ZIP API остаётся отдельной задачей. Для фактической проверки в GitHub использовать действующий сценарий `check-image-*` после разрешения на отправку тега. Публикация через `build-image-*`, слияние и обновление VPS выполняются по отдельному разрешению.
