# Сравнение Docling и текущего обработчика

Дата: 08.11.2026. Эксперимент не подключён к приложению. Рабочая БД читалась в режиме `mode=ro`; обработка выполнялась локально без OCR, платной LLM и сетевого доступа к моделям.

## Условия

Windows, Python 3.14.10, Docling Slim 2.137.0 / docling-core 2.106.0, BGE-M3 из локального `tokenizer.json`, HybridChunker с лимитом 512 токенов и объединением соседних элементов. Оба алгоритма считали размер одним токенизатором. Для текстов, ранее извлечённых из PDF, DoclingDocument собирался из абзацев текста; это не то же самое, что анализ исходного PDF.

Полная сборка Docling установлена отдельно; при первом запуске загрузка DLL задерживалась, при повторной диагностике PyTorch и SciPy запустились. Стандартный PDF-конвейер успешно проверен с локальной моделью разметки без OCR; результаты ниже. В Slim-режиме загрузка SciPy также зависала; в экспериментальных скриптах SciPy отключён на уровне процесса, OCR и анализ PDF моделью не использовались. Выводы не распространяются на стандартный PDF-конвейер Docling с моделью разметки. Зафиксированные пакеты: `requirements-slim.lock.txt`; приложения эти зависимости не затрагивают.

Текущий алгоритм работает по согласованному размеру, а не по пяти абзацам. Испытаны реальные файлы трёх разделов Pro Git из ZIP, git-status, извлечённый текст двух PDF и маленькие синтетические примеры Markdown/HTML. Для первых трёх Docling сообщил ошибку `SimplePipeline` с причиной `'>' not supported between instances of 'int' and 'NoneType'`. Это результат конкретной установленной версии и окружения, а не доказательство, что все AsciiDoc-файлы не поддерживаются.

## Сравнение

| Данные | Docling | Текущий алгоритм |
| --- | --- | --- |
| Pro Git, извлечённый PDF-текст, 918 795 символов | 720 основных чанков, медиана 453,5 токена, максимум 514, 80,8 с | 592 чанка, медиана 921 токен, максимум 1479, 6,2 с |
| Atlassian, извлечённый PDF-текст | 4 основных чанка, медиана 438,5, максимум 511, 0,70 с | 5 чанков, медиана 805, максимум 950, 0,034 с |
| git-status, текст в формате AsciiDoc | 13 чанков, 0,49 с, но заголовки не распознаны, значительная часть материала ошибочно определена как код | 27 чанков, 0,108 с; заголовки NAME, SYNOPSIS и другие распознаны |
| Три раздела исходной книги в AsciiDoc | Ошибка конвертации во всех трёх | Обработаны: 9, 11 и 22 чанка |
| Небольшие синтетические Markdown и HTML | Заголовки, список и блок команды выделены | Заголовки и команда выделены; в HTML текст списка извлечён без маркеров |

Размеры Docling в таблице — без перекрытия, текущие размеры уже включают перекрытие. Временем измерялись преобразование и чанкинг в одном предварительно запущенном процессе, без времени импорта; сравнение приблизительное. Пиковая RSS процесса Docling с загруженными библиотеками достигла примерно 746 МиБ. Отдельный процесс текущего алгоритма на тех же разделах достиг примерно 362 МиБ. Это не чистый расход конкретной библиотеки; процессы имеют разные наборы загруженных модулей.

В обеих обработках извлечённого текста Pro Git обнаружены все слова по счётчику нормализованных слов. Это грубая проверка: она не подтверждает порядок текста, корректность разметки и целостность предложений. Например, на Pro Git найдено 100 потенциальных разрывов предложений на границах соседних чанков Docling по простой эвристике; ручная выборка подтвердила случаи вида «Меня» / «по-прежнему ...». Сама сегментация предложений регулярным выражением тоже не даёт гарантии для сокращений, кода и многоязычных документов.

## Перекрытие

В параметрах установленного HybridChunker нет параметра overlap. Экспериментальный постобработчик в `compare.py` добавлял целый абзац, а при превышении 800 токенов — предложения, если они помещались. На Pro Git после такой надстройки: медиана 570,5, максимум 1004, 9 чанков более 800; перекрытие добавлено к 719 из 720 (весь файл без заголовков). Первоначальный вариант только с целыми абзацами дал 257 чанков свыше 800.

По новому уточнению владельца проверен также вариант только с предложениями (`sentence_overlap.py`): на Pro Git медиана 495, максимум 1004, 9 чанков более 800. Однако это пока не готовый безопасный алгоритм: если Docling уже оборвал предложение, копирование его хвоста не восстанавливает целую фразу. Нужно сначала исправлять границы или отдельно учитывать исходный текст. Границы разделов в этом опыте сравнивались по тексту заголовков; одинаковые названия разных разделов требуют более надёжных идентификаторов.

## Исходный PDF без моделей

Native PDF pipeline: Atlassian — одна страница за 5,43 с; Pro Git — первые 10 страниц за 1,19 с. Все проверенные элементы отмечены просто как `text`: заголовки и абзацы не определены, строки остаются отдельными. Native-режим не использует модель разметки и не решает поставленную задачу восстановления структуры; стандартный конвейер с моделью проверен отдельно, как описано ниже. Согласно официальной документации, Native PDF не восстанавливает порядок чтения, заголовки и таблицы: https://github.com/docling-project/docling/blob/main/docling/.agents/skills/docling/references/python-sdk.md

## Вывод и воспроизведение

Не заменять текущий обработчик по результатам испытания: имеются ошибки на трёх реальных AsciiDoc-источниках. Стандартный PDF-конвейер с локальной моделью улучшил заголовки и текст, но на проверенных страницах смешал команды и их вывод. Для технической базы предпочтительнее исходный текст с разметкой; PDF рассматривать только как источник, требующий проверки. Лёгкий Native PDF и работа с ранее извлечённым текстом не восстанавливают утраченную структуру.

`prepare_inputs.py` получает локальную выборку; `compare.py` запускает Docling и текущий парсер и сохраняет подробности в `.tmp/docling-results.json`; `baseline.py` отдельно измеряет текущий парсер; `native_pdf.py` проверяет PDF; `sentence_overlap.py` анализирует перекрытие. Установка и результаты остаются внутри проекта. Примеры HTML и Markdown синтетические. Автоматический поиск по тексту не заменяет ручной проверки содержания.

## Повторное испытание исходного PDF с моделью разметки

Стандартный PDF-конвейер Docling 2.137.0 успешно запущен 08.11.2026: CPU, локально скачанная модель разметки, `do_ocr=False`, `do_table_structure=False`, без сети во время обработки. Загрузку модели и разные документы выполняли в одном процессе: первая страница PDF Atlassian — 46,4 с с инициализацией, страницы 33–38 Pro Git — 10,81 с после загрузки; пик RSS процесса около 1417 МиБ. Это выборка шести страниц, а не измерение полной книги.

На Pro Git определены восемь заголовков, абзацы и списки, склеены многие переносы строк; текст значительно читабельнее Native. При этом команды из исходного PDF на странице 34 находились в трёх строках (`git add *.c`, `git add LICENSE`, `git commit ...`), а результат поместил их в одну строку внутри блока кода. Аналогично на странице 36 команда `git status` и несколько строк вывода соединены пробелами. Заголовки выгружаются одинаковым уровнем `##`, иерархия не проверена.

На одностраничной многостолбцовой шпаргалке Atlassian заголовки обнаружены, но отдельные описания и команды идут в неверном порядке, содержимое больших областей сериализовано как таблицы; например, объяснение `git clone` отделено от самой команды. Отключённое распознавание структуры таблиц — отдельное ограничение этого теста; поведение при включённом TableFormer не оценивалось.

Итог: стандартный Docling способен улучшить структурирование обычного текста PDF на рассмотренном образце, но проверка качества примеров команд обязательна. Ошибки не позволяют использовать результат как полностью надёжную базу для ответов. Подробный результат сохранён локально в `.tmp/standard-progit.pdf.md` и `.tmp/standard-atlassian-git-cheat-sheet.pdf.md`. Веса моделей — только в `.tmp/docling-models` и `.tmp/hf-cache`, не в рабочем приложении. `standard_pdf.py` воспроизводит опыт при наличии весов.
